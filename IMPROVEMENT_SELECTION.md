# Отбор и план внедрения улучшений AI Mobile Agent

**Дата:** 2026-10-15  
**Исходные материалы:** `temp/1`–`temp/5`, текущие `index.md`, тесты Playwright, quality sentinels и workflows GitHub Actions.  
**Цель отбора:** взять лучшие идеи, которые действительно соответствуют текущему приложению, дают измеримую пользу и не требуют рискованной миграции или новой инфраструктуры.

## Краткий итог

Не нужно внедрять весь список механически. В пяти файлах смешаны три разные категории: улучшения блогов на Jekyll, общие идеи для AI-чатов и конкретные предложения для AI Mobile Agent. Часть идей уже реализована в текущем приложении, а некоторые проекты из списка предполагают React/TypeScript/Vite, серверные URL или инструменты сборки, которых в этом vanilla-JS приложении нет.

Выбраны два дополнительных изменения в коде:
1. **Адаптивный бюджет истории на основе контекстного окна выбранной модели.** Если каталог провайдера сообщает `context_length`, история старых ходов сокращается по консервативному символьному бюджету, основанному на этом значении. Если контекстное окно неизвестно, используется прежний жёсткий предел 24 000 символов; сохраняются предел 24 сообщений и правило не разрывать ход диалога.
2. **Evidence-first журнал исследования.** Из URL, которые реально вернули веб-инструменты, извлекаются ограниченные записи источников: безопасная HTTPS-ссылка, заголовок, имя инструмента/источника и короткий выдержанный фрагмент. Журнал также сохраняет отпечаток эффективного системного промпта и размер промпта. Данные появляются в интерфейсе и экспортируются в Markdown/JSON.

Оба изменения аддитивны: старая история и старые журналы продолжают открываться, а старый способ экспорта сохраняется.

## Что уже есть и не нужно реализовывать второй раз

### Актуальные каталоги моделей и резервные попытки

В актуальном `main` уже есть каталоги провайдеров: загрузка, фильтрация текстовых моделей, поиск по ID/названию, кэш на шесть часов, отметка об устаревших данных и ограниченный fallback. Для каждого API используется подходящий маршрут; не все поставщики реализуют один и тот же endpoint. В список автопереключения не попадают устаревшие каталоги. Переключение на другую модель допускается лишь при распознанной ошибке конкретной модели; проблемы авторизации, квоты и временные серверные ошибки не должны превращаться в перебор моделей. Межпровайдерный резерв остаётся явным opt-in, потому что при нём текст задачи и контекст могут перейти другой компании.

Официальные API, на которые опираются адаптеры:
- [Gemini OpenAI compatibility](https://ai.google.dev/gemini-api/docs/openai)
- [Groq models](https://console.groq.com/docs/models)
- [xAI language models endpoint](https://docs.x.ai/developers/rest-api-reference/inference/models)
- [Pollinations model catalog](https://github.com/pollinations/pollinations/blob/main/gen.pollinations.ai/src/docs/models.md)
- [OpenRouter models](https://openrouter.ai/docs/api/api-reference/models/get-models)
- [Hugging Face Inference Providers hub API](https://huggingface.co/docs/inference-providers/en/hub-api)
- [Cloudflare Workers AI model search](https://developers.cloudflare.com/api/resources/ai/subresources/models/methods/list/)
- [NVIDIA NIM API](https://docs.nvidia.com/nim/large-language-models/latest/api-reference.html)

### Проверка всех настроенных GitHub Secrets

В `main` также слит workflow **Provider smoke test — all configured secrets**. Он ищет поддерживаемые варианты имен вроде `GEMINI_API_KEY` / `GEMINI`, `GROQ_API_KEY` / `GROQ`, `XAI_API_KEY` / `GROK`, `OPENROUTER_API_KEY` / `OPENROUTER`, `NVIDIA_API_KEY` / `NVIDIA`, `HF_TOKEN` / `HUGGINGFACE`, `CLOUDFLARE_API_TOKEN` / `CLOUDFLARE`. Для каждого найденного сервиса делается короткий реальный запрос; отсутствующие секреты пропускаются, ошибки одного провайдера не мешают проверить остальные. Значения ключей не выводятся в журнал. Pollinations browser App Key `pk_…` намеренно не считается серверным токеном для smoke-test; для такого теста нужен отдельный `sk_…`.

Важно: GitHub Actions Secrets доступны workflow на стороне GitHub, но не статическому Pages-приложению. Поэтому динамический каталог в браузере обновляется ключом, который введён в настройки приложения; один лишь секрет в GitHub Actions не может автоматически открыть браузеру доступ к платному/защищённому каталогу. См. [официальное руководство GitHub Secrets](https://docs.github.com/en/actions/reference/security/secrets).

### Другие существующие основы

В проекте уже есть исследовательский конвейер «план → исследователь → критик → синтезатор», ограничение раундов вызова инструментов, прямые публичные источники, проверка публичного HTTPS URL, базовая релевантная выборка пользовательской памяти, загрузка навыков по необходимости, кэш ответов по точному совпадению, экспорт/импорт профиля настроек без ключей, локальные резервные копии истории, журнал в Markdown/JSON и детерминированные браузерные регрессионные тесты. Предложения из `temp` не должны дублировать эти функции или удалять действующие ограничения.

## Принятые изменения в этом наборе

### 1. Бюджет истории с учётом известного контекста модели

Каталог моделей может сообщать размер контекстного окна. Когда это значение есть для выбранной модели и актуального каталога, код применяет к истории более строгий мягкий предел, рассчитанный из окна модели; верхний предел всё равно остаётся 24 000 символов. Когда каталог не содержит размера окна, используется прежний предел. История по-прежнему обрабатывается полными ходами и лимитом 24 сообщений.

Это **не точный tokenizer**: провайдеры и модели токенизируют языки, код и мультимодальные сообщения по-разному. Поэтому бюджет измеряется в символах и считается консервативной эвристикой, а не гарантией, что запрос точно укладывается в окно токенов. Последний ход сохраняется даже если он сам превышает soft budget — иначе можно незаметно потерять текущую задачу.

### 2. Источники из фактических результатов инструментов в журнале исследования

Журнал может содержать до 40 уникальных записей источников, только когда инструмент действительно вернул распознаваемый `URL: https://…`. При отображении и Markdown-экспорте ссылки повторно проверяются как публичные HTTPS; заголовок и фрагмент вставляются как текст, не как HTML. Существующие журналы без поля `sources` по-прежнему отображаются.

Это **не** означает, что каждое утверждение ответа автоматически связано с источником. Сейчас журнал фиксирует найденные источники и короткие выдержки, а не полноценный claim-evidence граф и не независимую оценку достоверности. Отсутствующая в ответе инструмента ссылка не выдумывается.

### 3. Метаданные промпта для диагностики

Записывается отпечаток фактически применённого системного промпта и его размер в символах. Это позволяет заметить, что два журнала создавались с разными инструкциями, не сохраняя отдельно дополнительную копию приватного промпта. Отпечаток не раскрывает содержимое промпта; его нужно трактовать как идентификатор версии, а не как доказательство качества ответа.

Сначала нужны воспроизводимый benchmark и регрессионные тесты. |
| WebLLM или локальные embedding-модели в браузере | Не внедрять по умолчанию | Большая первичная загрузка и нагрузка на мобильное устройство/память противоречат цели оставить приложение лёгким. Возможность можно дать как отдельную добровольную экспериментальную функцию. |

## Критерии готовности

Перед слиянием изменения должны пройти:
- разбор встроенного JavaScript и существующие Integrity/Security/Context sentinels;
- Jekyll build;
- Chromium E2E для модели с известным контекстным окном, источников из реального mock-инструмента, старого формата журнала и JSON-экспорта;
- браузерный smoke-test опубликованного сайта и успешный deploy Pages.

Реальные пользовательские API-ключи не читаются из GitHub и не вставляются в тесты. Live-провайдеры проверяются через workflow на стороне GitHub Actions, если он запускается пользователем; синтетические E2E-моки проверяют поведение без платных запросов к настоящим моделям.
