aLandi объединяет чаты, проекты, контекст и исследовательские инструменты в одной мобильной веб-среде. При желании её можно подключить к собственному gateway и локальной модели — без обязательного переезда на новую платформу.

Открыть рабочую среду ↗ Пошаговый запуск

Важно: сам интерфейс — бесплатная статическая страница GitHub Pages. Модельный inference, сторонние API и собственная инфраструктура в него не входят: их стоимость и условия определяются выбранным провайдером. Частный gateway, VPS и локальная модель настраиваются отдельно; публичный hosted AI endpoint этим сайтом не предоставляется.

▦

Проекты и контекст

Группируй чаты по проектам, используй инструкции и добавляй контекст к следующему запросу, не перестраивая весь рабочий процесс.

⌘

Подключаемый собственный gateway

Существующий клиент может работать с выбранным API. Для self-hosted варианта предусмотрен FastAPI gateway с авторизацией и локальным Ollama за закрытым интерфейсом.

⌕

Исследование с источниками

Поиск и работа с источниками встроены в рабочий процесс. Доступность конкретных инструментов зависит от конфигурации, сетевых ограничений и выбранного провайдера.

▤

Документы — по отдельному разрешению

Локальное извлечение PDF, DOCX и XLSX предусмотрено в gateway, но функция отключена по умолчанию и требует отдельной проверки перед включением.

◖

Голос — опциональный этап

Адаптеры локального ASR/TTS существуют, но голосовые флаги остаются выключенными до проверки конкретных моделей, лицензий, устройства и задержек.

◎

Сначала небольшой стек

Первый контур не требует кластера сервисов: статический клиент, один API gateway и одна активная модель. Дополнительные базы и workers добавляются только под измеренную потребность.

Запуск — по измеримым шагам

Сначала безопасный минимальный контур. Документы, голос и дополнительные агенты — только после отдельной приёмки.

Проверить клиент и CI.
Убедиться, что текущий Pages deployment доступен; PR-head checks не заменяют post-merge deployment.
Инвентаризировать существующий VPS.
Проверить ОС, архитектуру, RAM, диск, процессы, порты и уже работающие сервисы. Не переустанавливать всё поверх существующей инфраструктуры.
Развернуть модель и gateway локально.
Проверить авторизацию, allowlist модели, лимиты и loopback bind до публикации hostname.
Подключить HTTPS Tunnel и браузер.
Только после локальных проверок. Проверить ошибочные ключи, обычный completion, кэш и рестарт после reboot.
Граница первого релиза.

Текущая сборка ориентирована на личный/ограниченный сценарий, а не на открытый многопользовательский SaaS. Один bearer key в браузерном хранилище не является достаточной системой multi-user auth. До публичного пользовательского запуска нужны отдельные аккаунты/сессии, лимиты, защита от злоупотребления и проверенная политика хранения данных.

Частые вопросы

Мне обязательно покупать VPS?

Нет, чтобы открыть опубликованный интерфейс. VPS нужен для собственного self-hosted gateway и локальной модели. Сначала проверь, не существует ли уже подходящий сервер и не занят ли он другими сервисами.

Данные всегда остаются локальными?

Нет универсальной гарантии: маршрут данных зависит от выбранного провайдера и настроек. Собственный локальный gateway может сократить передачу внешним AI-провайдерам, но нужно проверять конфигурацию, логи, резервные копии и все включённые функции. Не отправляй чувствительные данные в непроверенный маршрут.

Работают ли документы и голос сразу?

Нет. Извлечение документов и ASR/TTS требуют настроенного gateway, совместимых локальных артефактов и отдельных включённых флагов. Лицензии, качество и задержки должны быть проверены до активации.

Можно сразу приглашать других пользователей?

Нет — сначала нужно спроектировать и проверить multi-user authentication, разграничение данных, квоты, обработку секретов и поддержку. Текущий личный контур не следует считать готовым публичным SaaS.
