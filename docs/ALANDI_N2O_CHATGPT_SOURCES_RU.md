# aLandi N₂O — руководство по ChatGPT Project Sources

**Версия:** 1.0  
**Назначение:** определить компактный, полезный и поддерживаемый набор постоянных источников ChatGPT Project.  
**Важно:** GitHub остаётся каноническим хранилищем; Project Sources — вручную поддерживаемая рабочая копия, не зеркало с автоматической синхронизацией.

## 1. Принцип отбора

В Sources следует добавлять не всё, что может пригодиться, а только документы, которые:
- существенно меняют качество и безопасность ответов;
- используются регулярно;
- имеют ясную область действия и владельца;
- не дублируют друг друга;
- обновляются с понятной частотой.

Большой архив не равен хорошему контексту. Подробные справочники подключать по необходимости, а не постоянно.

## 2. Рекомендуемый постоянный набор

Начать с пяти документов:

| Файл в GitHub | Роль в Sources | Частота пересмотра |
|---|---|---|
| `AGENTS.md` | инженерные правила, безопасность, границы полномочий и протокол работы с репозиторием | при изменении инженерных правил |
| `docs/ALANDI_N2O_CORE_RU.md` | стабильная конституция N₂O: evidence, authority, security, status semantics | редко |
| `LOOP.md` | цикл инженерной работы от наблюдения до обучения и rollback | при изменении процесса |
| `docs/ALANDI_N2O_KNOWLEDGE_LOOP_RU.md` | как извлекать, проверять, продвигать и пересматривать уроки | при изменении метода обучения |
| `docs/ALANDI_N2O_CHATGPT_SOURCES_RU.md` | этот индекс: назначение источников и правила синхронизации | при изменении набора |

Это стартовый компактный набор, а не обязательный максимум. Если Project ограничивает объём/количество Sources, приоритет: CORE → AGENTS → LOOP → KNOWLEDGE LOOP → этот индекс.

## 3. Подключать по задаче, не держать постоянно

| Документ | Когда подключать |
|---|---|
| `DECISIONS.md` | архитектурные изменения, противоречия, выбор вариантов |
| `EVALS.md` | тестирование, benchmark, качество, критерии приёмки |
| `INTEL.md` | поиск актуальных моделей, API, библиотек и upstream |
| `docs/TECHNIQUE_REGISTER_RU.md` | исследование практик, open-source проектов и методов |
| `docs/ALANDI_MASTER_CONTEXT_RU.md` | глубокая работа с архитектурой и границами продукта |
| `docs/PROJECT_STATE.yaml` | восстановление текущего состояния, feature flags и рисков |
| `ORIENTER.md` и `project-reference/FILE_ORIENTER_RU.md` | навигация и контрольная точка; всегда сверять с live GitHub |
| `docs/VOLLEY_LOG.md` | хронология существенных этапов и решений |

Не загружать весь репозиторий в Project Sources. Для файлового вопроса сначала искать нужный фрагмент в GitHub/Files, затем подключать точечный источник.

## 4. Что не следует закреплять как постоянный контекст

- Текущие HEAD, PR queue, статусы CI и deployment: они быстро устаревают.
- Большие логи, полные диффы и временные отчёты.
- Дублирующие версии одного ADR, backlog или state snapshot.
- Непроверенные идеи, случайные conversation dumps и сгенерированные графы.
- Секреты, персональные данные, пользовательские prompts и содержимое приватных файлов без отдельного основания.

Динамическое состояние проверяется непосредственно в GitHub перед инженерной работой. Копия `ORIENTER.md` в Sources не освобождает от live-проверки.

## 5. Синхронизация GitHub → Project Sources

1. Сначала обновить канонический документ в GitHub через согласованную ветку и PR.
2. Проверить содержимое и результат проверки/ревью.
3. Определить, изменился ли один из файлов постоянного набора.
4. Если изменился — заменить соответствующий Project Source вручную; не добавлять рядом копию с новым названием.
5. Проверить дату/версию в источнике и удалить устаревшую копию через штатные средства управления Sources, если она больше не нужна.
6. Не считать обновление GitHub автоматическим обновлением загруженного файла ChatGPT.

Для оперативной задачи можно передать актуальный файл прямо в разговор/Work, не меняя постоянный набор.

## 6. Протокол начала инженерной задачи

- Проверить актуальный branch, HEAD, PR и его ограничения.
- Прочитать `ORIENTER.md`, подробный ориентир и `docs/PROJECT_STATE.yaml` на нужной ветке, если это часть задачи.
- Проверить live GitHub main, открытые PR/issues и exact-head checks.
- Открыть только связанные исходники, тесты и архитектурные документы.
- Не считать Project Sources доказательством текущего состояния репозитория.

## 7. Протокол завершения

После значимого этапа:
- обновить существующие канонические документы;
- зафиксировать SHA, ветку/PR, файлы, реально выполненные проверки и ограничения;
- синхронизировать только затронутые постоянные Sources;
- сообщить владельцу, какие файлы Sources нужно заменить и почему.

## 8. Основание по организации инструкций

Подход согласуется с актуальной документацией GitHub: общие инструкции следует держать короткими и конкретными; специализированные правила разделять по назначению/области применения; не перегружать глобальный контекст деталями, нужными лишь отдельным типам задач. Это принцип организации, а не утверждение, что механизмы GitHub Copilot автоматически применяются к ChatGPT Projects.
