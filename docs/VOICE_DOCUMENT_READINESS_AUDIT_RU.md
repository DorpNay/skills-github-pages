- **Голосовой ввод:** UI и путь записи → локальный ASR endpoint → редактируемая расшифровка покрыты E2E с mock MediaRecorder и mock gateway. Реальный микрофон, совместимость кодеков, whisper.cpp и модель на целевом устройстве не подтверждены.
- **Озвучивание ответа:** UI-кнопка, локальный TTS endpoint, mini-player и выбор только реально установленного allowlisted Piper voice существуют; E2E использует mock WAV. Реальная установка Piper, выбранная voice model, её лицензия/hash, воспроизведение на iOS и задержка не подтверждены.
- **Диалог голосом:** PR #60 добавил прототип half-duplex цикла. Это не непрерывный streaming voice: VAD, streaming ASR, barge-in/перебивание, управление очередью TTS, маршрутизация аудио и echo cancellation остаются отдельными задачами.

- **Подключение UI документов:** E2E подтверждает, что PDF из attachment flow отправляется на настроенный aLandi gateway, а извлечённый текст добавляется в запрос как недоверенные справочные данные. Это тест с подменёнными ответами, не реальный end-to-end запуск.
- **Инфраструктура:** gateway, Ollama, ASR/TTS runtime, модели и Cloudflare Tunnel на VPS не подтверждены как совместно работающие.

## Принципы реализации

1. Не называть mock E2E доказательством реального микрофона, модели, синтеза речи или сервера.
2. Голос и бинарное извлечение остаются выключенными, пока оператор явно не установил runtime, проверил лицензии/хэши артефактов и включил флаги.
3. Исходные аудио/документы не должны незаметно попадать в долговременную память, логи или response cache. Передавать только по явному действию пользователя; извлечение/аудио ответы должны иметь `Cache-Control: no-store`.
4. Расшифровка до отправки остаётся редактируемой. Запись и TTS должны иметь доступный Stop/Cancel, который отменяет активный запрос и не позволяет устаревшему ответу запустить воспроизведение.
5. Текст документа/транскрипта — недоверенное содержимое, а не инструкции системе. Сохранять происхождение источника; не исполнять инструкции из вложений.
6. Не обещать OCR, распознавание видео-аудио, Google Drive sync, real-time streaming или многопользовательскую безопасность без соответствующего runtime и тестов.
7. На личном статическом клиенте API key в браузерном хранилище — только прототип для одного владельца; это не серверная multi-user авторизация.

## Отдельное продуктовое требование: живой разговор и выбор голоса

Транскрипция голосового сообщения и разговорный голосовой режим — разные сценарии. Оба должны быть доступны явно, а не объединены в одну кнопку.

### UX и режимы

- [~] **Голосовое сообщение:** UI/code path реализован; пользователь может записать фрагмент, отредактировать расшифровку и отправить вручную. Реальный микрофон/модель на целевом устройстве ещё не проверены.
- [~] **Живой разговор (первый этап — half-duplex):** прототип цикла есть, но это не streaming/full-duplex. Проверить реальные ASR/TTS, задержку, отмену, echo и состояние UI на устройстве.
- [ ] Переключение в живой режим не включается само собой; видимые Start/Stop и разрешение микрофона обязательны. Stop прекращает запись, ASR, запрос модели и воспроизведение настолько полно, насколько позволяют используемые API.
- [x] **Выбор установленного голоса:** PR #75 добавил allowlisted список preinstalled Piper voices из authenticated `/v1/capabilities` и UI selector; API валидирует voice ID. Остаются выбор конкретных packs, artifact-specific license/SHA-256, реальный синтез и UX-проверка на устройстве.
- [ ] Для локального TTS показывать только голоса, чьи файлы и runtime действительно установлены и прошли проверку. Если доступен один голос, не рисовать второй фиктивный вариант.
- [ ] Голос хранится как предпочтение выбранного режима/чата согласно принятой модели настроек; не передавать это предпочтение внешнему провайдеру, если синтез остаётся локальным.
- [ ] При смене языка выбирать совместимый установленный голос либо объяснять, что голос недоступен; не делать тихий fallback на внешний сервис.
- [ ] Расшифровка и ответ видны текстом, если пользователь не включил отдельный режим аудио-only. Пользователь может исправить распознанный текст до отправки.

### Архитектурный контракт живого режима

1. Сначала завершить стабильный **half-duplex** цикл на текущем локальном ASR/TTS: микрофон → ASR → запрос выбранному провайдеру → локальный TTS → воспроизведение.
2. Добавить единый state machine и отмену задач: `idle → listening → transcribing → thinking → speaking → idle`; ошибка возвращает интерфейс в восстанавливаемое состояние. Поздний результат отменённого запроса не должен отправляться или проигрываться.
3. Не выдавать half-duplex за «разговор в реальном времени»: пользователь ждёт завершения реплики и ответа. Для следующего этапа нужны измеренные streaming ASR, VAD/end-of-turn, потоковый вывод модели, потоковый TTS, аудиобуфер и обработка перебивания.
4. До добавления VAD/barge-in проверить акустическое эхо от динамика в микрофон, поведение при Bluetooth/гарнитуре, блокировке экрана и системном звонке. Без AEC непрерывное прослушивание может повторно распознавать голос самого помощника.
5. Предусмотреть push-to-talk как надёжный fallback, если браузер/устройство не поддерживает требуемый режим. Не обещать постоянное фоновое прослушивание мобильного браузера.
6. В первой версии сохранять выбранный маршрут модели и правило ручного переключения собственного/стороннего провайдера. Никакого автоматического переключения на другой провайдер при ошибке.
7. Метрики приёмки: время от отпускания кнопки до финального ASR, до первого токена/начала ответа, до первого аудиофрейма; длительность TTS; ошибки и отмены; пиковая RAM. Замерить отдельно на целевом устройстве и VPS.

### Как понимать «мужской и женский голос»

Это UX-фильтр для установленных голосовых моделей, не отдельный синтезатор. Реализация должна перечислять реальные локальные voice packs и их метаданные. Перед включением проверить лицензию и SHA-256 каждой модели; не скачивать и не менять голосовую модель молча. Наличие Piper в коде само по себе не подтверждает, что конкретные русские/английские голоса установлены или звучат приемлемо.
