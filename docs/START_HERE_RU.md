# aLandi — начать с нуля (короткая инструкция владельцу)

**Дата:** 28 октября 2026  
**Цель:** подключить существующий AI Mobile Agent к приватному gateway и одной локальной модели на VPS.  
**Не делай:** не создавай второй сайт; не публикуй API keys; не открывай наружу порт 8000 или 11434; не удаляй существующий Dify/Tunnel.

**Выбранная локальная модель и пошаговая установка:** [UNCENSORED_MODEL_AND_FREE_CPU_RUNBOOK_RU.md](UNCENSORED_MODEL_AND_FREE_CPU_RUNBOOK_RU.md).

## 1. Открой уже существующий клиент

1. Открой https://dorpnay.github.io/skills-github-pages/.
2. Открой GitHub Actions: https://github.com/DorpNay/skills-github-pages/actions.
3. Проверь, что последний Pages deployment имеет статус **success**. CI PR-head — это не то же самое, что опубликованный deployment.
4. Если сайт открывается, переходи к VPS. Если deployment красный, сначала исправь его — не переходи к серверу.

## 2. Определи: VPS уже есть или нет

**Если VPS уже есть:** открой его Console и выполни диагностические команды из раздела 2 полного руководства. Не переустанавливай Ollama и не меняй firewall, пока не выяснишь, что уже работает.

**Если VPS нет:** открой [Vultr signup](https://www.vultr.com/register/), создай аккаунт и проверь итоговую стоимость, тариф, регион, оплату и дату окончания любого кредита до Deploy. Для этого проекта целевой профиль — Ubuntu 24.04 LTS, x86_64, 4 vCPU / 8 GB RAM. Это целевой профиль, а не уже купленный сервер и не гарантия бесплатного тарифа.

## 3. Создай постоянный API hostname

1. Войди в [Cloudflare Dashboard](https://dash.cloudflare.com/).
2. Подключи свой домен и дождись активной DNS-зоны. Если домена нет — сначала зарегистрируй его у регистратора и проверь стоимость продления.
3. Открой **Networking → Tunnels**. Если Tunnel уже используется другим сервисом, не удаляй его.
4. Создай отдельный Tunnel или добавь hostname к существующему.
5. Для native cloudflared на VPS настрой Published application route: hostname, например `llm.ТВОЙ-ДОМЕН`; service URL — `http://127.0.0.1:8000`.
6. Не открывай порты 8000/11434 в firewall. Tunnel должен идти исходящим соединением и направлять HTTPS hostname на loopback gateway.

## 4. Установи модель и gateway на VPS

Открой VPS Console и выполняй **по порядку**:

1. Полный гайд → раздел 2: диагностика ОС, памяти, диска, портов и служб.
2. Раздел 3: установка Ollama, bind только на приватный интерфейс, одна модель `qwen3.5:4b`, context 4096 и concurrency 1.
3. Раздел 4: отдельный Linux user `alandi`, checkout репозитория, Python venv, закрытый `/etc/alandi-gateway.env`, systemd service.
4. Раздел 5: локальные проверки. Не переходи к Tunnel, пока:
   - `/healthz` возвращает 200;
   - `/v1/models` без ключа возвращает 401;
   - авторизованный каталог содержит разрешённую модель;
   - completion возвращает ответ;
   - повтор exact-запроса показывает cache HIT;
   - оба порта слушают только приватный интерфейс.
5. Раздел 6: подключи Tunnel и проверь hostname с реальным API-запросом.
6. Раздел 7: в AI Mobile Agent выбери **aLandi Self-hosted Gateway**, укажи HTTPS hostname + `/v1`, точный model ID и API key.
7. Раздел 8–11: проверь кэш, мониторинг, backup и rollback.

**Секрет:** `ALANDI_API_KEY` генерируется на VPS и хранится только в `/etc/alandi-gateway.env` с правами `600`. Не вставляй его в GitHub, публичный исходник, issue или этот чат.

## 5. Проверка «готово»

Система готова к твоему обычному использованию только когда всё ниже подтверждено лично на твоём endpoint:

- [ ] Pages deployment успешен, сайт открывается.
- [ ] VPS: Ollama и gateway активны.
- [ ] Gateway доступен только через Tunnel; публичные порты 8000/11434 закрыты.
- [ ] HTTPS hostname отвечает; неправильный API key получает 401.
- [ ] Из чата проходит реальный completion через gateway.
- [ ] Cache MISS → повтор HIT; bypass действительно обходит cache.
- [ ] После перезагрузки VPS gateway и Tunnel запускаются автоматически.
- [ ] Сохранены backup env/config и инструкции rollback (сам секрет — отдельно и защищённо).

## 6. Первый успешный запрос: текст → документ → голос

Базовый gateway сначала должен пройти разделы 2–7 полного руководства: /healthz = 200, неавторизованный /v1/models = 401, авторизованный completion возвращает текст, а gateway/Ollama слушают только loopback. Только после локальных проверок подключай HTTPS hostname через Tunnel.

### 6.1 Текстовый запрос

1. В AI Mobile Agent выбери **aLandi Self-hosted Gateway**.
2. Укажи адрес вида https://llm.ТВОЙ-ДОМЕН/v1, модель, которая реально присутствует в ollama list, и API key из закрытого env-файла на VPS.
3. Отправь короткий безличный запрос. Успех — ответ отображён в текущем чате и gateway отвечает с корректной авторизацией. Не публикуй ключ и не вставляй его в этот документ.

### 6.2 Документный запрос (только локальный gateway)

1. Сначала проверь наличие ALANDI_DOCUMENT_EXTRACTION_ENABLED=false в env-файле. Установи/проверь актуальную версию gateway и её зависимости, сделай резервную копию env и проверь что локальные /v1/capabilities и /healthz отвечают с ожидаемой авторизацией.
2. Выбери один поддерживаемый файл PDF, DOCX или XLSX размером меньше лимита ALANDI_DOCUMENT_EXTRACTION_MAX_BYTES (по умолчанию 8 MiB). Включение этой функции требует осознанного изменения на VPS: ALANDI_DOCUMENT_EXTRACTION_ENABLED=true, затем перезапуск gateway и повторная проверка /v1/capabilities. Не включай флаг, если текущий код/парсер/формат не проверены.
3. В интерфейсе выбери собственный aLandi gateway, прикрепи файл и отправь конкретный вопрос по его содержимому. Клиент передаёт файл только на настроенный gateway; извлечённый текст рассматривается как недоверенные данные. Успех — ответ опирается на содержимое тестового файла, а не просто подтверждает его наличие.
4. Если capability выключена, запрос получает ошибку или формат не поддержан — остановись и проверь gateway logs/config; не переключайся молча на внешний сервис. После проверки можно вернуть флаг в false.

### 6.3 Голос: три отдельных сценария

Голосовые функции не включены по умолчанию. До установки конкретных локальных артефактов оставь ALANDI_AUDIO_TRANSCRIPTION_ENABLED=false и ALANDI_AUDIO_SPEECH_ENABLED=false. Сверяйся с [планом голоса и инструкцией установки](VOICE_IMPLEMENTATION_PLAN_RU.md).

1. **Запись → транскрипция:** установи локальные whisper.cpp/модель и ffmpeg/ffprobe, проверь источник, лицензию и SHA-256. Включи только ALANDI_AUDIO_TRANSCRIPTION_ENABLED=true, проверь capabilities, затем запиши короткую тестовую фразу. Транскрипт должен появиться в редактируемом поле и **не отправляться автоматически**.
2. **Голосовой диалог в текущем чате:** после успешной транскрипции отправь тестовую реплику явно и проверь, что ответ модели появляется в том же чате. Это существующий half-duplex путь, а не доказательство streaming/VAD/AEC/barge-in.
3. **Озвучивание любого сообщения:** установи Piper runtime и конкретные заранее загруженные voice artifacts. Для каждого голоса проверь отдельную лицензию и SHA-256; в каталог допускаются только согласованные .onnx + .onnx.json. Настрой ALANDI_AUDIO_SPEECH_VOICES=voice-id=Label, включи ALANDI_AUDIO_SPEECH_ENABLED=true только после проверки файлов, и проверь отдельную кнопку озвучивания, mini-player, выбор голоса и Stop.

Не скачивай модели автоматически и не включай оба голосовых флага одновременно «на пробу». После каждого изменения проверяй /v1/capabilities авторизованным запросом и возможность отката. Никогда не открывай порты 8000/11434 наружу: публичный путь должен идти через настроенный HTTPS Tunnel, а origin — на loopback.

### 6.4 Что CI не доказывает

PR #75 добавил выбор только предварительно установленных Piper voices и был объединён после успешных exact-head Gateway, Quality/Chromium/Pages-smoke и provenance checks. Это подтверждает контракт кода и mock-тесты, но не наличие моделей на VPS, их пригодность/лицензию, работу реального микрофона, качество речи или производительность. Перед первым live-запуском проверь актуальный Pages deployment и post-merge CI в [GitHub Actions](https://github.com/DorpNay/skills-github-pages/actions); статус PR-head не заменяет эти проверки.
