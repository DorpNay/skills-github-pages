# aLandi — карта потоков данных и вводные для Privacy Notice

**Внутренний предпусковой документ. Не является юридическим заключением и не готов к публикации как окончательная политика.** Его цель — зафиксировать фактические data flows и не допустить маркетинговых утверждений, которые код/инфраструктура пока не доказывают.

## 1. Подтверждённые факты текущей архитектуры

| Данные / событие | Где обрабатывается или хранится | Что сообщать до дополнительной проверки |
|---|---|---|
| Статический клиент | GitHub Pages, затем браузер пользователя | GitHub Pages не запускает backend-модель; при открытии сайта хостинг может обрабатывать технические сведения соединения по своим правилам |
| История чатов и настройки | Браузерное хранилище; текущий код использует localStorage, отдельные данные — IndexedDB | Данные привязаны к браузерному профилю/сайтовому origin; очистка данных сайта, профиль браузера, extensions и доступ к устройству влияют на конфиденциальность и сохранность |
| Ключи API выбранных провайдеров, включая собственный gateway | Текущая клиентская реализация сохраняет ключи настроенных провайдеров в localStorage, в том числе ключ собственного aLandi gateway | Это удобство личного прототипа, не серверный vault и не защита от XSS/расширений/других пользователей того же профиля. Не использовать общий профиль браузера и не представлять это как multi-tenant secret storage |
| Обычный chat request | Браузер → выбранный пользователем endpoint/provider; отправленный контекст может включать историю/выбранный контекст | Получатель определяется текущими настройками и маршрутизацией. Нельзя утверждать, что сообщение всегда остаётся на устройстве или что внешний провайдер никогда его не получает |
| Собственный aLandi gateway | HTTPS hostname через Cloudflare Tunnel → FastAPI gateway → локальная Ollama на VPS | Для self-hosted маршрута владелец контролирует VPS, но необходимо отдельно учитывать хостинг VPS, Cloudflare Tunnel, DNS, модельные артефакты, логи и backup |
| Серверный response cache | Gateway может сохранять точные завершённые ответы в SQLite согласно текущей конфигурации кэша | До публикации надо раскрыть фактический cache TTL, что является ключом кэша, что хранится в значении и как выполняется удаление/backups; не обещать нулевое хранение |
| Документы | Встроенное локальное извлечение поддерживается gateway, но feature flag по умолчанию выключен | Не включать и не писать, что обработка включена, пока версия gateway, флаг, parser limits, временные файлы и логирование не проверены на реальном VPS |
| Голос | Локальные ASR/TTS адаптеры/интерфейс есть в коде; функции отключены по умолчанию | До проверки конкретных бинарников, модели, голоса, лицензии, временных файлов и target-device тестов не обещать рабочую голосовую функцию |
| Браузерная личная/общая память | Текущий PR #86 содержит изменения IndexedDB private/shared separation, но ещё не входит в main | Не выдавать поведение PR за опубликованное. Даже после merge shared store останется локальным для браузера, не облачной синхронизацией |

Эта таблица описывает только то, что известно из репозитория. Реальные VPS, Cloudflare, DNS, модель и их настройки пока нельзя считать проверенными без действий владельца.

## 2. Что обязательно подтвердить владельцу перед публичным Privacy Notice

Заполни этот реестр в локальной копии, не публикуя личные сведения в issue/PR, пока не решено, какие из них публичны.

- [ ] Оператор: физическое лицо или юридическое лицо, публичное имя/бренд и юридический адрес, если применимо.
- [ ] Контакт для запросов на доступ/удаление и вопросов приватности (лучше отдельный адрес поддержки; не выдумывать адрес до его создания).
- [ ] География оператора, хостинга, предполагаемых пользователей и целевые страны запуска.
- [ ] Целевая аудитория и минимальный возраст, если применимо.
- [ ] Будет ли это личный интерфейс одного владельца, ограниченная beta по приглашениям или публичный многопользовательский продукт.
- [ ] Реальная схема входа и авторизации: сейчас отдельная multi-user auth система не подтверждена.
- [ ] Точные домены, hosting providers, Tunnel mode/plan и фактически подключённые внешние AI/search providers.
- [ ] Какие данные собираются: чаты, выбранный контекст, проекты/инструкции, вложения, provider settings, browser storage, server-side cache, diagnostic logs, billing/support messages.
- [ ] Retention по каждой категории: browser data, server cache, logs, temporary files, backup copies. Если срок неизвестен, сначала измерить/проверить, а не угадывать.
- [ ] Реальная политика удаления и экспорта: что удаляется сразу, что остаётся в резервных копиях и когда копии ротируются.
- [ ] Фактическая обработка Cloudflare/GitHub Pages/VPS и внешнего провайдера: metadata/access logs, location/jurisdiction, applicable terms.
- [ ] Используются ли analytics, cookies beyond essential browser storage, tracking pixels, telemetry или third-party frontend assets.
- [ ] Как обрабатываются запросы об удалении, security incident, credential compromise и закрытии аккаунта, если появится account system.
- [ ] Кто отвечает за support и стоимость вычислений; есть ли автоматические биллинговые ограничения/quotas.

## 3. Текущий список запретов на маркетинговые формулировки

Не публиковать без отдельного доказательства следующие заявления:

- «Все данные всегда остаются только на устройстве».
- «End-to-end encrypted» / «шифрование сквозное».
- «Ничего не сохраняем» / «zero logs» / «полное удаление без следов».
- «Автоматическая облачная синхронизация всей памяти между устройствами».
- «Безопасно для корпоративных/медицинских/финансовых/секретных данных».
- «Поддерживается полностью автономный voice assistant, realtime barge-in или эхоподавление».
- «Публичный SaaS готов к регистрации любого числа пользователей».
- Любое обещание доступности, p95 latency, model quality или ежемесячной цены до реального измерения.

Разрешённая осторожная формулировка: пользователь выбирает провайдера/endpoint; личный self-hosted путь доступен после самостоятельной настройки gateway; документы и голос требуют отдельного включения и проверки. Это не отменяет необходимости перечислить фактические стороны, участвующие в обработке.

## 4. Каркас будущего клиентского уведомления

После проверки пунктов раздела 2 итоговое уведомление должно простым языком объяснять:

1. Кто является оператором и как связаться по privacy-вопросам.
2. Что делает статическая страница и какие данные остаются в browser storage.
3. Что отправляется выбранному AI/search provider при отправке запроса.
4. Что меняется при подключении собственного gateway: маршрут до VPS, роль Tunnel, серверный cache/logs/backups.
5. Какие функции отключены по умолчанию (документы, voice, экспериментальная память) и что происходит при ручном включении.
6. Сроки хранения, экспорт/удаление, ограничения резервных копий и необходимые действия самого пользователя.
7. Как меняется уведомление при появлении пользователей/аккаунтов/платной подписки.

**Публикационный gate:** владелец проверил фактическую инфраструктуру и юрисдикцию, заменил утверждения только подтверждёнными фактами и получил независимую юридическую проверку там, где она необходима. Этот файл — checklist для подготовки, не финальная политика.
