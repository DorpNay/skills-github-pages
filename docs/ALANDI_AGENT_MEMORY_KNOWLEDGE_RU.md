# aLandi: агентная система, память-граф и знания

**Версия плана: 2026-10-21.** Это целевая архитектура, а не утверждение, что ещё не реализованные функции уже работают в опубликованном приложении.

## Решение

Не запускать 60+ отдельных моделей одновременно. Создать каталог из 64 специализированных логических ролей, исполняемых как лёгкие профили/навыки поверх доступной модели. Оркестратор выбирает 1–3 роли для обычной задачи, 3–7 для исследования; больше — только при явном запросе и наличии бюджета. Отдельные маленькие модели включаются лишь после общего benchmark. Так сохраняется идея «60+ агентов» без 60 процессов или копий весов.

### Вызов и ресурсы

- Fast: 0–1 роль; не запускать swarm на приветствиях.
- Deep/Research: 2–5 ролей; сетевые fetch можно распараллелить.
- Coding: planner → implementer → independent reviewer → tests.
- На VPS 8 GB параллелизм генерации по умолчанию 1; не держать несколько весовых файлов в RAM.
- Каждая задача получает max_steps, deadline, бюджет, cancellation и проверяемое условие остановки.
- Роли не равны отдельным моделям. Не утверждать, что отдельные агенты реально запускались, если это не так.

## Память как граф нитей

### Слои

1. История сообщений — первоисточник, не переписывается.
2. Рабочая память чата — временные сущности, цели, ограничения, решения, незакрытые вопросы и ссылки на сообщения; пустая в новом чате.
3. Память проекта — доступна другим чатам только при включённом «Использовать память проекта».
4. Глобальная память пользователя — только явно сохранённые предпочтения/факты, если включена.
5. Процедурная память — проверенные навыки и lessons, отдельно от пользовательских фактов.
6. Evidence store — URL, выдержки, дата, hash документа и точное место.

Узлы: Person, Project, Conversation, Message, Fact, Decision, Goal, Constraint, OpenQuestion, Source, Document, Skill, Evaluation, Lesson.

Рёбра: MENTIONS, SUPPORTS, CONTRADICTS, SUPERSEDES, DEPENDS_ON, PART_OF, DERIVED_FROM, APPLIES_TO, DECIDED_IN, RESOLVES, RELATED_TO.

Каждый факт должен иметь id, text, type, scope, source_message_id/document_id, created_at, valid_from/valid_until, confidence, status (candidate/confirmed/disputed/superseded/rejected), sensitivity и user_approved_at при необходимости.

### Правила памяти

1. Не сохранять chain-of-thought. Сохранять краткие решения, основания, открытые вопросы и evidence pointers.
2. Извлечение создаёт кандидатов, не подтверждённые истины.
3. Дедуплицировать по сущности/значению/времени; при конфликте не затирать историю, создавать CONTRADICTS/SUPERSEDES.
4. Стабильные предпочтения требуют подтверждения; временные детали получают TTL.
5. Перед ответом извлекать top-k релевантных узлов по задаче, scope, свежести и доверию; не грузить весь граф.
6. Пользователь может просматривать, исправлять, экспортировать и удалять узлы и производные индексы.
7. Чувствительные данные не переносятся между проектами автоматически.
8. «Обучение на каждом шаге» означает candidate lesson → regression eval → версионирование → promotion/rollback, не бесконтрольное изменение весов или production prompt.

## Проекты, документы и Google Drive

Проект включает название, инструкции, чаты, источники, память и sharing settings. В каждом чате нужны переключатели: только память чата; память проекта; глобальная память; выбранные источники проекта/Drive. Безопасный default: чатовая память включена, project/global memory выключены, пока пользователь не согласился. Перемещение чата — явное действие с preview scope и отменой.

Импорт документов: локальный upload с allowlist типов; парсинг; чанки с overlap; document_id/hash/title/page/sheet/section/offsets; индекс; retrieval; цитирование точного места. Не помещать документы в system prompt целиком и не передавать их внешнему провайдеру без предупреждения. Для больших/сканированных PDF — отдельный OCR worker с лимитами.

Google Drive: OAuth client secret и refresh token нельзя размещать в статическом Pages/localStorage как production-схему. Нужны backend OAuth callback, state/PKCE, минимальные read-only scopes, зашифрованный token vault, явный file picker, revoke/disconnect, аудит и удаление. Сначала read-only, только выбранные файлы, синхронизация hash/mtime.

## RAG и мультимодальность

Старт: локальный импорт → нормализация → SQLite FTS5 → retrieval → citations. Embeddings/reranker добавлять только если golden set докажет улучшение. Для мультимодальных документов заимствовать подход RAG-Anything: парсинг текста/таблиц/формул с page/bbox provenance; тяжёлый parser — отдельный worker. Метрики: Recall@5, MRR, citation precision, answer support rate, contradiction recall, p50/p95 latency, peak RSS, индексный размер.

Изображения/видео/аудио должны быть отдельными provider/worker adapters. HyperFrames — HTML/CSS/media-to-MP4 renderer, а не text-to-video модель. OCR не равен ASR; ASR не равен TTS. Один worker за раз, лимиты размера/длительности, отмена, cleanup временных файлов и отсутствие raw media в логах.

## Персонализация

Профиль: preferred name (optional), style, user instructions, language, verbosity. Проект: project instructions, memory scope, sources, model/tool policy. Диалог: overrides, sources, summary/open tasks. Приоритет: safety/system → workspace policy → project instructions → user preferences → current message. Пользовательские инструкции не отключают безопасность и не повышают права инструментов.

## Очерёдность и критерии готовности

P0: scope/privacy schema + golden set. P1: проекты, project instructions, memory toggles, import/export/delete. P2: SQLite FTS5, provenance, citations, SSRF-protected fetch. P3: 64-role catalog + bounded router + event timeline. P4: eval-gated learning. P5: isolated OCR/ASR/image/video workers. P6: OAuth integrations after backend token vault.

DoD: нет cross-project leakage; каждый memory fact имеет provenance/scope/status/delete; конфликты не затираются; citations указывают место; skills не влияют на fast mode без нужды; tests покрывают injection, stale facts, deletion, citations и privacy boundaries; никакой агент не получает shell/network/secrets автоматически.
