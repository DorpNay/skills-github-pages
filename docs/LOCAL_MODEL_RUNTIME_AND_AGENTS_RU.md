# Локальные модели, GPU offload и агентские роли aLandi

**Дата исследования:** 2026-10-28. Источники — официальные документы Ollama, llama.cpp и модельные карты Qwen. Все рекомендации ниже учитывают текущий репозиторный hardware profile, а не предполагают, что у неизвестного VPS есть GPU.

## Короткий вывод: «без CPU» не существует как полноценный режим сервера

GPU может выполнять основную математику инференса, но CPU всё равно нужен для ОС, сетевого сервера, подготовки запросов, токенизации/части runtime, дискового ввода-вывода и оркестрации. Практически достижимая цель — **GPU-ускорение с минимальным CPU bottleneck**, если на сервере есть поддерживаемый GPU и достаточно VRAM, чтобы избежать нежелательного spill/offload в системную память.

Официальная документация Ollama предлагает проверять фактическое размещение через `ollama ps`. Колонка `PROCESSOR` различает `100% GPU`, `100% CPU` и смешанное распределение. Не считать наличие драйвера или CUDA достаточным доказательством: решает фактический runtime report после загрузки модели.

## Что подтверждено о целевом оборудовании проекта

В `infra/hardware_profiles.yaml` есть профиль `laptop_8gb_cpu_mvp` с `ram_gb: 8`, `gpu: none`, статусом `target_not_benchmarked` и лимитом одной активной LLM concurrency. Это профиль разработки/целевой baseline, а не результат измерения VPS. Пока неизвестно, какой CPU, RAM, swap, GPU/VRAM и драйверы реально доступны на production-сервере.

Следовательно, **сейчас нельзя обоснованно настраивать GPU-only, CUDA, ROCm или vLLM как рабочую конфигурацию**. Сначала выполнить read-only инвентаризацию `scripts/diagnose_model_runtime.sh` на самом сервере.

## Рекомендуемая модельная схема для 8 GB RAM без GPU

| Роль | Кандидат | Политика |
|---|---|---|
| Основной диалог | `qwen3.5:4b` | Единственная постоянно используемая модель; сохранить контекст 4096 и concurrency 1 до замеров |
| Ручное сжатие памяти проекта | `qwen3.5:0.8b` | Кандидат для существующего `ALANDI_HELPER_MODEL`: он обслуживает ручные предложения компактных фактов; кандидаты не сохраняются автоматически. Это не универсальный router. |
| Экспериментальный второй helper | `qwen3.5:2b` | Сравнить с 0.8B только на labelled set; общего маршрутизатора агентских задач пока нет. Не загружать одновременно с основной моделью без RAM-замеров. |
| Независимый multilingual challenger | `llama3.2:1b` | Официальный Ollama tag около 1.3 GB, контекст 128K; отдельная лицензия Meta Llama и фактическое качество RU/TH требуют проверки. Не считать заменой Qwen без eval. |
| Очень маленький structured-task challenger | `granite4:350m` | Официальная Ollama страница указывает Apache 2.0 и tool-calling/text-extraction сценарии, но опубликованный список языков не включает русский/тайский. Рассматривать только для English-side задач после eval, не для RU/TH маршрутизации. |
| Детерминированный fast path | существующие exact-template rules | Предпочитать правила там, где результат однозначен; не тратить inference на приветствия/простые шаблоны |
| Речь | whisper.cpp + Piper | Отдельные процессы; измерять пиковую RAM и не запускать тяжёлые ASR/TTS и LLM конкурентно |

Qwen3.5-0.8B и 2B — реальные компактные варианты из официальных модельных карт. Текущий `ALANDI_HELPER_MODEL` используется для ручных предложений сжатия памяти проекта; generic classification/tool-routing endpoint ещё не реализован. Наличие параметров 0.8B/2B не доказывает качество на конкретных агентских задачах. Любой будущий JSON router обязан проходить schema validation, ограничения размера/времени, негативные тесты и безопасный fallback; он не получает права исполнять инструменты самостоятельно.

Для альтернативного сравнения полезны официальные страницы [Llama 3.2 в Ollama](https://ollama.com/library/llama3.2) и [Granite 4 в Ollama](https://ollama.com/library/granite4). Это кандидаты, а не утверждение, что один из них лучше Qwen на aLandi. Не скачивать сразу все варианты: сначала базовый Qwen 4B, затем один Qwen 0.8B helper; альтернативу добавлять только если тестовый набор показывает конкретную выгоду.

На 8 GB **не держать 4B + 2B + ASR одновременно в памяти**. Пусть Ollama переключает модели по требованию; учитывай цену выгрузки/загрузки и измеряй cold/warm latency. Сначала сравнить основной Qwen 4B с rule-based routing, затем добавить только один helper, если golden set показывает реальную пользу.

## Если диагностика обнаружит GPU

### NVIDIA

Официальная документация Ollama перечисляет совместимые GPU и требования драйвера; на момент исследования указаны compute capability 5.0+ и драйвер 550+, с более строгими требованиями к некоторым старым поколениям. Убедиться, что драйвер и контейнер/служба действительно видят устройство. После тестового запроса проверить `ollama ps`; для NVIDIA дополнительно сохранить `nvidia-smi` и VRAM utilization.

### AMD / Intel / Vulkan

Ollama описывает ROCm для определённых AMD GPU и дополнительную поддержку через Vulkan; поддержка зависит от конкретной модели GPU, ОС и драйверов. Не устанавливать ROCm или Vulkan пакеты вслепую на неизвестный VPS. Сначала зафиксировать `lspci`, драйвер, runtime logs и версию Ollama, затем следовать официальному списку поддерживаемых устройств.

### Выбор runtime

- **Ollama** — основной вариант для текущего gateway: минимальная миграция, OpenAI-compatible API и встроенный GPU placement report.
- **llama.cpp** — CPU build и несколько GPU backends (CUDA, HIP, Vulkan, SYCL и другие); имеет смысл, если нужно явно контролировать offload layers или Ollama не использует нужное устройство. Переход потребует отдельной сборки, unit/service и повторного контрактного тестирования gateway.
- **vLLM** — не выбирать для профиля без GPU как способ «освободить CPU». Это другой serving stack, и его полезность зависит от совместимого accelerator/VRAM, модели, batch/concurrency и конкретной нагрузки. Не мигрировать без реального GPU-инвентаря и сравнительного benchmark.

## План измерения КПД

Собрать до/после по одному и тому же тестовому набору, на одной версии модели и одинаковом контексте:

- p50/p95 time-to-first-token и full response latency;
- токены/с, время cold load и warm run;
- peak RSS/PSS системы, VRAM peak, swap activity;
- CPU utilization, GPU utilization, температура/ограничение частоты;
- 10–30 типовых запросов: простой, extraction JSON, tool routing, длинный контекст, русская речь через ASR;
- точность/валидность структурированных ответов и долю fallback/повторов.

Не объявлять GPU-конфигурацию быстрее по одной метрике или на синтетическом одном запросе. Цель — лучший end-to-end результат при сохранении памяти, приватности и устойчивости gateway.
