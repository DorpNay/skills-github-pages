# aLandi — первый стек, предпусковой чек-лист и план владельца

**Статус:** проектное решение и runbook-план на 2026-10-28. Это не подтверждение, что VPS, DNS, Tunnel, модель или multi-user сервис уже развёрнуты.

## 1. Решение: какой стек запускаем первым

Рекомендуемый первый выпуск — **личный/закрытый beta для одного владельца**, а не открытый многопользовательский SaaS.

| Слой | Первый выбор | Почему | Условие готовности |
|---|---|---|---|
| Лендинг | Отдельная статическая страница **landing/index.html** в существующем GitHub Pages/Jekyll проекте | Не ломает текущий корневой AI Mobile Agent; один источник кода и один Pages deployment | Jekyll build, quality checks, Chromium и опубликованный Pages smoke проходят на точном SHA |
| Приложение | Существующий HTML/CSS/JavaScript client на GitHub Pages | Не переписывать рабочую основу и не добавлять frontend framework без доказанной необходимости | Smoke в Chromium, ручной тест на целевом мобильном устройстве |
| API | FastAPI gateway на Python, отдельный Linux user **alandi**, systemd | Уже существующий gateway и его тесты — минимальный путь вместо нового backend | Unit/security tests, auth/CORS/allowlist/body/timeouts, restart/reboot проверены |
| Модельный runtime | Ollama на том же VPS, bind только на loopback | Минимум сервисов, одна модель и отсутствие публичного Ollama API | Фактические RAM, latency и стабильность измерены на целевом VPS |
| Модель baseline | **qwen3.5:4b**, context 4096, concurrency 1 — только первый кандидат для измерения | Уже отражено в install guide; можно сравнить с меньшей моделью при нехватке RAM/скорости | Холодный/тёплый запросы, peak RAM, p50/p95 и поведение под нагрузкой записаны |
| Входящий трафик | Cloudflare Tunnel с отдельным hostname → **http://127.0.0.1:8000** | Исходящий tunnel избавляет от прямой публикации origin-портов | HTTPS hostname, корректный auth, rate limits и ограничения доступа проверены |
| Секреты | ALANDI_API_KEY и Tunnel credentials только на сервере; env-файл с правами **600** | Нельзя размещать их в публичном репозитории или клиентском JavaScript | Проверено отсутствие секретов в diff, logs, workflow artifacts и публичных URL |
| Данные | Существующая браузерная история/IndexedDB; gateway SQLite и bounded exact-response cache по текущей реализации | Не добавлять отдельную базу до доказанной необходимости | Backup/restore и политика хранения проверены вручную; тестовое удаление имеет ожидаемый результат |
| Наблюдаемость | systemd status/journal, health/capability checks, лимитированный лог без prompts, аудио и секретов | Достаточно для закрытого пилота; не притворяется полноценным observability stack | Ошибки 401/5xx, рестарт, заполнение диска и недоступность модели можно диагностировать |

### Что сознательно не включать в первый выпуск

- Dify, Redis/Valkey, PostgreSQL, Qdrant/Weaviate и отдельный embedding service.
- Несколько одновременно загруженных LLM, автоматический multi-agent оркестратор и GPU runtime без подтверждённого совместимого GPU.
- OCR для сканированных PDF, realtime streaming voice, VAD/AEC/barge-in и автоматическое извлечение памяти.
- OAuth/Google Drive, мультиаккаунты, общую облачную синхронизацию браузерной памяти или платёжные функции.
- Публичную регистрацию пользователей на едином bearer key.

Добавлять компонент можно только под конкретный сценарий, измерение/тест и проверенный бюджет.

## 2. Главная граница публичного запуска

Нынешний клиент — статический интерфейс, а не скрытый backend. GitHub Pages не запускает FastAPI/Ollama и не защищает ключи, встроенные в публичный исходник.

Для первого закрытого пилота нельзя выдавать один общий bearer key за multi-user систему. Пока нет отдельных пользовательских сессий, разграничения данных, квот и abuse protection, лендинг должен говорить о **собственном gateway / личном развёртывании**, а не обещать всем посетителям готовую облачную AI-службу.

Перед открытой регистрацией понадобятся отдельный design/security review по следующим пунктам: аутентификация и восстановление доступа, изоляция между пользователями и проектами на сервере, лимиты затрат и скорости, политика логирования/удаления, rate limiting, защита от prompt injection и злоупотребления инструментами, incident response и поддержка.

## 3. Точные предположения для первого хоста

Ориентир из текущего runbook — Ubuntu 24.04 LTS x86_64, примерно 4 vCPU / 8 GB RAM и SSD/NVMe. Это профиль для проверки, не купленный ресурс и не обещание производительности. Ubuntu 24.04 находится в стандартном security maintenance до мая 2029 года; если на момент заказа доступен Ubuntu 26.04 LTS, **не меняй версию импульсивно**: сначала проверь systemd/install scripts, пакеты и CI, затем обнови runbook и acceptance tests единым изменением.

Модель **qwen3.5:4b** занимает ориентировочно 3.3–4.0 GB диска по официальной библиотеке Ollama. Размер файла не равен пиковому потреблению RAM: нужны память для runtime, KV/context cache, ОС и прочих процессов. Поэтому держим одну модель, context 4096 и concurrency 1. Если при тесте OOM/сильный swap/неприемлемая latency — остановись, сними измерения и сравни **qwen3.5:0.8b** отдельно; не загружай обе модели одновременно постоянно.

Тег модели не является неизменяемой версией: снимки официальной библиотеки показывают изменение short ID между публикациями. До установки зафиксируй `ollama --version`, точный tag, digest из `ollama list`, а также `ollama show <tag>` (quantization, template, parameters и license). После pull сохрани фактический идентификатор/манифест установленного артефакта в provenance record; повторно сверяй лицензию и digest, а не копируй старое значение из runbook. Реестр в текущем срезе показывает `qwen3.5:4b-q4_K_M` с Apache-2.0, но это не заменяет проверку фактически установленного артефакта. Native context в карточке модели не является рекомендуемым runtime context: оставь 4096 до измерения RAM/latency на целевом хосте.

Источники для сверки версий и поведения:
- [Ubuntu 24.04 release notes и поддержка](https://documentation.ubuntu.com/release-notes/24.04/)
- [Ollama — Qwen3.5 model library](https://ollama.com/library/qwen3.5)
- [Cloudflare Tunnel docs](https://developers.cloudflare.com/tunnel/)
- [GitHub Pages: что это и чего он не делает](https://docs.github.com/en/pages/getting-started-with-github-pages/what-is-github-pages)

## 4. До заказа сервера: действия владельца

### Шаг 1. Проверить существующую инфраструктуру

1. Открой [текущий клиент](https://dorpnay.github.io/skills-github-pages/) и убедись, что он открывается.
2. Открой [GitHub Actions](https://github.com/DorpNay/skills-github-pages/actions) и отдельно проверь последний Pages deployment. PR CI не заменяет успешную публикацию на main.
3. Установи, есть ли уже VPS и используется ли он другими сервисами. Не создавай дубликат и не удаляй существующие Dify/Tunnel/containers.
4. Если VPS есть, до любых изменений зафиксируй ОС/архитектуру, CPU, RAM, swap, свободный диск, активные systemd services и listen addresses. Не публикуй в отчёте env values, токены, IP, если они тебе не нужны для разбора.

### Шаг 2. Проверить бюджет и домен

1. Если VPS ещё нет — до кнопки Deploy проверь цену тарифа, регион, диск, налоги, оплату, окончание trial/credits и цену продления. Не считать рекламный кредит гарантированным.
2. Если домена нет, выбери и зарегистрируй его только после проверки цены продления и прав на управление DNS. Для Cloudflare Tunnel опубликованный hostname требует домен, подключённый к Cloudflare.
3. Реши, нужен ли отдельный поддомен API, например **llm.example.net**; в публичных документах оставляй только placeholder. Не вставляй реальный hostname, ключи или Tunnel token в GitHub issue/PR, этот чат или клиентский код.

### Шаг 3. Подтвердить целевой профиль

- [ ] Есть доступ к имеющемуся VPS либо подтверждена итоговая цена нового.
- [ ] ОС/архитектура совместимы с выбранным runbook.
- [ ] Достаточно RAM/диска после учёта уже работающих сервисов и модели.
- [ ] Известно, кто имеет SSH/root access и как восстановиться при неудачном обновлении.
- [ ] Домен, DNS и план ежемесячных затрат понятны.
- [ ] Никакие существующие сервисы не будут удалены/перенастроены без инвентаризации.

**Не переходи к установке**, если неизвестно, что уже работает на хосте, или если бюджет/доступ/backup не подтверждены.

## 5. Этапы развертывания — только после проверки владельцем

Используй [короткий стартовый чек-лист](START_HERE_RU.md) и затем [полный install guide](ALANDI_IMPLEMENTATION_GUIDE_RU.md). Не дублируй/не перепрыгивай его проверочные шаги; ссылки ниже указывают порядок.

### Этап A — инвентаризация и резервные копии

- Read-only инвентаризируй CPU/RAM/GPU, диск, Ollama, systemd и listen addresses. Скрипт **bash scripts/diagnose_model_runtime.sh** добавляется в PR #86, но пока не находится в main; используй его только после merge/review этого PR и предварительного просмотра файла. До этого применяй read-only команды из раздела 2 [полного install guide](ALANDI_IMPLEMENTATION_GUIDE_RU.md), не копируя непроверенный script на сервер. Не выводи содержимое .env.
- Сделай резервную копию существующей конфигурации и проверь процедуру её восстановления.
- Проверь, что доступ по SSH-ключу настроен и текущая SSH-сессия не является единственным способом входа, который будет потерян при firewall changes.
- Не меняй firewall, Tunnel, systemd units и Ollama bind до сопоставления фактического состояния с runbook.

### Этап B — минимальная модель

- Установи только одну модель, если её ещё нет и подтверждён бюджет памяти/диска.
- Проверь локальный completion через Ollama и запиши model tag, версию Ollama, время холодного/тёплого запроса и peak RAM.
- Поставь начальный context 4096 и concurrency 1. Не делай выводов о качестве русского/тайского и о производительности без тестового набора на реальном хосте.

### Этап C — FastAPI gateway

- Используй отдельного пользователя **alandi**, Python venv и service unit из актуальной инструкции.
- Сгенерируй новый случайный ALANDI_API_KEY непосредственно на VPS; не отправляй его в чат и не записывай в репозиторий. Положи его в защищённый env-файл, права 600, владелец/группа проверены.
- Разреши только выбранную модель и точный CORS origin **https://dorpnay.github.io** без пути и завершающего слеша.
- Убедись, что gateway слушает только **127.0.0.1:8000**, Ollama — только **127.0.0.1:11434**; не публикуй эти порты напрямую.
- Документы и голос оставь выключенными до отдельной приёмки. Не включай feature flags массово.

### Этап D — обязательные локальные gates

Пока Tunnel не настроен на внешний hostname, на самом VPS подтверди:

- [ ] /healthz возвращает ожидаемый HTTP 200.
- [ ] Неавторизованный /v1/models возвращает HTTP 401.
- [ ] Авторизованный /v1/models показывает только разрешённую модель.
- [ ] Небольшой completion завершается и возвращает модельный ответ.
- [ ] Повтор exact-запроса даёт ожидаемый cache HIT, а cache bypass действительно работает.
- [ ] Порты 8000 и 11434 слушают только loopback.
- [ ] В логах нет API ключа, пользовательского prompt, приватного документа или сырого аудио.
- [ ] Права env/config соответствуют инструкции; service перезапускается без ручного shell state.

Если хотя бы один gate не прошёл — не подключай публичный hostname; исправь причину или откати изменение.

### Этап E — Cloudflare Tunnel и HTTPS

1. Создай новый tunnel или используй существующий только после выяснения его текущих маршрутов и зависимостей.
2. Добавь отдельный hostname → **http://127.0.0.1:8000**.
3. Проверь, что вход доступен только через предусмотренный HTTPS маршрут; публичные порты origin остаются закрытыми.
4. Проверь корректный ключ, неправильный ключ (401), rate-limit/timeout и поведение при недоступном origin. Не оставляй временный Quick Tunnel как постоянный production URL.
5. Не публикуй Tunnel token и config secrets в PR/репозитории.

### Этап F — подключение клиента

1. Открой приложение и явно выбери собственный aLandi gateway.
2. Укажи HTTPS hostname с суффиксом /v1, точную модель из авторизованного /v1/models и ключ, сгенерированный на VPS.
3. Отправь безличный тест без приватных данных.
4. Проверь неверный key, сетевой timeout, cache HIT, cache bypass и отсутствие тихого переключения на стороннего провайдера.
5. Для личной памяти проверь, что запрос остаётся на локальном маршруте. Не используй реальную секретную/рабочую информацию как первый тест.

### Этап G — reboot, backup и rollback

- [ ] Перезапусти gateway и Ollama, проверь health/capabilities после рестарта.
- [ ] Перезагрузи VPS в согласованное окно и подтверди автозапуск сервисов/Tunnel.
- [ ] Сделай backup конфигураций и необходимой SQLite data; секреты хранить отдельным защищённым способом.
- [ ] Проверь restore на безопасной копии, прежде чем считать backup рабочим.
- [ ] Подготовь rollback: отключить hostname/tunnel route; вернуть предыдущий env/config; восстановить known-good commit/service unit; проверить health. Не удалять данные, volumes и старые сервисы ради чистоты.

## 6. Отдельные функции после первого успешного текстового запроса

Включать строго по одной, каждый раз с backup, одним feature flag и собственным acceptance test:

1. **Документы:** проверить capability discovery, размеры и типы файлов; начать с безопасного небольшого PDF/DOCX/XLSX, проверять локальную обработку и отсутствие тихого внешнего fallback. Сканированные PDF/OCR отдельно.
2. **Голос:** проверить exact SHA-256, происхождение и лицензию движка, checkpoint, голоса и phonemizer; затем latency/RSS, реальный микрофон/звук, качество RU/TH на целевом устройстве. До этой приёмки все voice flags выключены.
3. **Память:** текущий PR #86 разделяет browser-local private/shared stores и имеет зелёный CI, но перед merge/production требуется интеграционная проверка project scopes, миграции, отмены promotion, внешних provider routes и ручного восстановления. Это не облачная межустройственная синхронизация.
4. **RAG:** два синтетических smoke-запроса не являются benchmark. Перед заявлением об улучшении retrieval собери не менее 50 разрешённых, обезличенных, вручную размеченных запросов и сравни baseline/candidate на тех же данных.
5. **GPU:** ничего не устанавливать до фактического подтверждения GPU, VRAM, совместимого драйвера и выгодного benchmark; ollama ps — один из runtime checks, а не замена тесту нагрузки.

## 7. Финальный Definition of Done перед закрытым пилотом

### Код и сайт
- [ ] Все выбранные PR проверены по актуальному HEAD и нужным required checks; после merge повторно проверены main Quality и Pages deployment.
- [ ] Лендинг не обещает работающий hosted endpoint, автоматическую синхронизацию, включённый voice/OCR или multi-user SaaS, если это не подтверждено.
- [ ] Проверены mobile layout, клавиатура/viewport, навигация, доступность клавиатурой и отсутствие внешних обязательных JS-зависимостей на лендинге.
- [ ] Все ссылки и инструкции ведут к актуальным путям; нет несуществующих contact/support обещаний.

### Сервер и безопасность
- [ ] API работает за HTTPS Tunnel; origin ports закрыты; auth/CORS/allowlist/limits проверены.
- [ ] Модель не превышает заданный RAM/latency budget под тестом; restart and reboot проверены.
- [ ] Секреты не попали в git/history/logs/artifacts.
- [ ] Backup восстановлен в тестовой копии; rollback известен.
- [ ] Есть владелец расходов, мониторинг диска/RAM и расписание обновлений.

### Продукт и политика
- [ ] Определён закрытый круг первых пользователей и путь обратной связи.
- [ ] На лендинге раскрыты ограничения и зависимость от пользовательского gateway.
- [ ] Подготовлены Terms/Privacy policy только под фактические data flows; не писать «данные никогда не покидают устройство», если может быть выбран внешний provider.
- [ ] Для открытого multi-user доступа отдельно спроектированы auth/session, tenant isolation, quotas, abuse controls, cost controls и retention/deletion. До этого не выдавать личный beta за публичный SaaS.

Перед написанием клиентской политики используй внутреннюю [карту потоков данных и вводные для Privacy Notice](LAUNCH_PRIVACY_REVIEW_RU.md). Этот файл специально не подключён как публичная политика: юридические и инфраструктурные факты ещё должен подтвердить владелец.

## 8. Действия, которые остаются только за владельцем

Эти действия нельзя выполнить безопасно из GitHub-репозитория: подтвердить существующий VPS и его службы, принять расходы, владеть доменом/DNS, сохранить production credentials, проверить доступ к серверу, испытать реальный микрофон/динамик и подтвердить, что backup восстанавливается. Не передавай секреты агенту — выполняй команды самостоятельно по runbook.

После каждого этапа передавай для проверки только обезличенный итог: ОС/архитектура, CPU/RAM/диск, названия активных служб, HTTP status codes, доступный model ID, capability flags, p50/p95 и пиковую RAM. Убери API keys, Tunnel tokens, prompts, документы, публичный IP, если раскрытие не требуется для отдельной безопасной процедуры.

**Рекомендуемый порядок:** сначала review лендинга и всех PR → подтверждение бюджета/существующего хоста владельцем → минимальный текстовый gateway → безопасный Tunnel → закрытый пилот → отдельная приёмка документов, памяти и голоса → только затем решение об открытом релизе.
