## 1. Для чего нужен этот документ

Это передача контекста следующему чату, чтобы продолжить работу без повторного опроса владельца и без выдумывания состояния инфраструктуры. Источник истины — файлы репозитория, актуальные проверки и явные решения владельца. Архитектурное намерение не означает, что инфраструктура уже настроена или работает.

## 2. Подтверждённые решения владельца

### Главный приоритет ближайшего этапа — принцип 15
Развернуть первую полноценную качественную версию aLandi на сервере, протестировать собственную модель и подключить задуманные функции в удобном и достойном для использования виде. Сразу использовать современные, проверенные инженерные практики и проверяемую реализацию, чтобы не переделывать конструкцию с нуля. После первой версии функции можно постепенно улучшать. Владелец регулярно перепроверяет этапы разработки.

Полный реестр принципов 1–15: [docs/ALANDI_REQUIREMENTS_REGISTER_RU.md](ALANDI_REQUIREMENTS_REGISTER_RU.md).

### Задуманная цепочка запроса
1. Пользователь отправляет сообщение через существующий сайт GitHub Pages.
2. Запрос безопасно доходит по HTTPS до gateway на собственном VPS.
3. Gateway проверяет доступ и маршрутизирует запрос к собственной локальной модели.
4. Модель отвечает; gateway возвращает ответ в браузерный интерфейс.

### Архитектурное направление
- Сохранить существующий статический мобильный интерфейс; не создавать второй сайт и не переписывать `index.md` на React без отдельного обоснования.
- GitHub Pages остаётся статическим UI, а не сервером для FastAPI или модели.
- Планируемая серверная часть: небольшой FastAPI gateway и Ollama с одной активной моделью.
- Планируемый безопасный внешний доступ: Cloudflare Tunnel/Access и постоянный API hostname.
- Gateway и Ollama должны слушать только loopback: ожидаемые адреса `127.0.0.1:8000` и `127.0.0.1:11434`. Не открывать эти порты напрямую в интернет.
- Стартовая модель, записанная в архитектурных документах: `qwen3.5:4b`, контекст 4096, один параллельный инференс. Это плановая конфигурация, пока не подтверждённая фактическим замером на сервере.
- Не добавлять без необходимости новые базы, дополнительные сервисы и несколько оркестраторов до стабилизации базовой цепочки.

## 3. Безопасность — обязательные проверки

- Не публиковать API keys, токены Tunnel или другие секреты в `index.md`, публичных workflow и репозитории.
- Не выставлять FastAPI/Ollama напрямую в интернет.
- Проверить аутентификацию gateway, CORS allowlist для фактического origin сайта, маршрутизацию, лимиты тела запроса, timeout и ограничение параллельности.
- Проверить, что неавторизованный запрос отклоняется, авторизованный запрос к каталогу моделей проходит, а тестовый prompt проходит весь путь до модели и обратно.
- Проверить реальный Cloudflare Tunnel, hostname/DNS и доступность маршрута извне; не считать Tunnel настроенным только потому, что он описан в документации.
- Не удалять и не перенастраивать существующие Tunnel, Dify или сетевые службы без инвентаризации текущего VPS.

## 4. Что известно о состоянии, а что нет

### Подтверждено файлами репозитория
- Существует клиентский файл `index.md` с интерфейсом AI Mobile Agent.
- В репозитории есть код gateway/FastAPI и документация по Ollama и Cloudflare.
- В руководстве `docs/ALANDI_IMPLEMENTATION_GUIDE_RU.md` указано, что ранее CI проверял клиентскую сборку и браузерные тесты; это не доказывает работоспособность живого VPS.
- Короткое руководство владельца: `docs/START_HERE_RU.md`.
- Архитектурный документ: `docs/SUPERSTACK_FINAL_RU.md`.
- Реестр требований 1–15: `docs/ALANDI_REQUIREMENTS_REGISTER_RU.md`.

### Не подтверждено текущей проверкой
- Что VPS уже существует, доступен и настроен.
- Что Ollama установлена и модель действительно загружена/работает на VPS.
- Что FastAPI gateway запущен как служба и доступен локально.
- Что Cloudflare Tunnel создан, активен, привязан к нужному домену и маршрутизирует запрос на gateway.
- Что внешняя цепочка «GitHub Pages → Tunnel → gateway → Ollama → ответ в браузере» прошла end-to-end тест.
- Что последний GitHub Pages deployment прямо сейчас успешен. Это нужно проверить в GitHub Actions; исторический успешный CI не заменяет проверку актуального deployment.

**Важно:** наличие кода, документации или зелёных CI job не является доказательством работающей production-инфраструктуры.

## 5. Следующие действия — в безопасном порядке

1. Открыть [GitHub Actions](https://github.com/DorpNay/skills-github-pages/actions) и подтвердить статус последнего опубликованного Pages deployment.
2. Уточнить по фактам, есть ли уже VPS. Если да — сначала только диагностировать ОС, RAM/disk, слушающие порты, службы, контейнеры и текущий Tunnel. Ничего не удалять и не переустанавливать до аудита.
3. Проверить локально на VPS Ollama и gateway, не открывая порты наружу. Следовать `docs/START_HERE_RU.md` и соответствующим разделам `docs/ALANDI_IMPLEMENTATION_GUIDE_RU.md`.
4. Проверить gateway auth и health/model endpoints по руководству; сохранить фактические результаты и ошибки без секретов.
5. Проверить или настроить Cloudflare Tunnel и hostname, сохраняя существующие маршруты и записи DNS.
6. Выполнить сквозной тест от браузера до собственной модели и обратно. Зафиксировать фактическую задержку, ошибки, RAM и статус каждой ступени.
7. После подтверждения базовой цепочки подключать остальные функции по одной, с тестами и проверяемыми результатами.
8. Передавать владельцу отчёт: что проверено, какие команды/тесты выполнены, результаты, что не проверено, риски и следующий шаг.

## 6. Принципы взаимодействия следующего чата

- Не просить владельца повторять то, что уже есть в этом документе или репозитории.
- Не путать требуемое состояние с фактическим.
- Не придумывать результаты команд, тестов, статусы инфраструктуры, домены или секреты.
- Сначала читать существующие файлы, рабочую ветку и изменения; избегать дублирующих документов и ненужных переписываний.
- Делать небольшие обратимые изменения; сохранять пользовательские изменения.
- Проверять технические факты по официальной документации, если от версии/API зависит решение.
- Отчитываться только о реально выполненных проверках.
- Окончательное решение о слиянии в `main` остаётся за владельцем.
